# Architecture and engineering decisions

## Foundation

Electron + electron-vite + React + TypeScript, packaged with electron-builder. Exact resolved dependencies are committed in `pnpm-lock.yaml`; Electron, packaging tools and Sharp are explicitly pinned. Node 24+ is required for development/tests. No backend, authentication, telemetry or runtime network dependency.

- `src/main`: application lifecycle, folder dialogs, installation preferences, database/migrations and validated IPC handlers.
- `src/preload`: a narrow `window.cards` facade, no raw IPC, Node, SQL or filesystem exposure.
- `src/shared/contracts.ts`: operation/result types, metadata keys, page size and serial formatting; safe in either process.
- `src/renderer`: React UI, ordered autosave controller; no database/filesystem imports.
- `tests`: storage, migrations, autosave and real Electron UI/relaunch checks.

### SQLite choice

Use Electron's bundled `node:sqlite` `DatabaseSync` rather than a separately compiled native addon. Electron supports this builtin (the missing builtin was fixed in Electron PR 47706); it ships with each supported Electron platform/architecture. This removes addon ABI rebuilds, prebuilt binary selection and ASAR unpack rules. Only long-established DatabaseSync/statement APIs are used. Node's SQLite API has carried experimental/release-candidate status; this is an explicit tradeoff for packaging simplicity. Pin Electron, exercise the bundled database in desktop/package tests, and revalidate on upgrades. A small repository service keeps a future driver swap contained.

Synchronous short SQLite operations run in main. This is intentionally simple for a personal catalogue. Bounded reads (100 rows) ordered by indexed fixed-width serial prevent whole-library rendering. Archive ZIP/checksum work uses streaming filesystem operations; move database or archive work to a dedicated worker only if measured workloads warrant it. No ORM or server.

### Library layout

```
<chosen folder>/
  catalogue.sqlite
  catalogue.sqlite-wal       # SQLite managed while open
  catalogue.sqlite-shm       # SQLite managed while open
  media/originals/<card UUID>/<photo UUID>.<source extension>
  cache/thumbnails/<card UUID>/<photo UUID>.jpg
```

New libraries require an empty directory. Existing libraries require a recognized migration table; missing/unrecognized databases are not silently recreated. Opening creates missing cache/media directories. If remembered library cannot open, show an error and allow explicit selection, preserving the old location and files. Do not delete/move a live library or put it on a network/shared-sync filesystem. This app provides no synchronization.

Original image bytes are copied into the application-owned media tree and never resized or recompressed during normal viewing. User filenames are retained only as display metadata; stable card/photo UUIDs provide filesystem identity. Thumbnails are separate 720×720-bound, auto-oriented JPEG files generated by Sharp at quality 86. They are cache data and may be recreated from the original when requested. Relative paths are stored in SQLite so an entire library remains movable while closed.

`userData/preferences.json` contains the installation UUID, last library folder, a machine-local public-site output folder keyed by immutable library UUID, and one machine-local `lastPhotoImportDirectory`. Writes use a flushed temporary file and atomic rename. Malformed installation identity or site-folder mapping fails visibly instead of silently issuing a new identity. The public output and photo-picker locations are not catalogue content and are not included in `.cug` archives, avoiding stale paths after moving to another computer. Workstation names and all range history live in the library database keyed by installation UUID, so relevant names/ranges accompany the catalogue. Names are per-library for the same installation (intentional decision; avoids a second settings synchronization mechanism). A newly installed copy opening an existing library must configure its own allocation. The UI does not expose the internal UUID or remembered photo directory.

The single main-process `photos:choose` handler serves Full Card, Corner, Edge, Additional and Replace native pickers. Before opening Electron's native dialog it checks the remembered absolute path with platform-native `isAbsolute` and `statSync`; a missing, inaccessible, non-directory or non-native path simply omits `defaultPath`. After `Library.importPhotos()` has validated, copied and persisted at least one selected image, main derives the first file's parent with Node `dirname`/`resolve` and atomically updates preferences. Cancelled dialogs and failed imports leave the prior value unchanged. Drag/drop remains on the separate `photos:import` IPC route and cannot change picker history. No preference path crosses the typed preload boundary.

Migration 5 adds an immutable, database-owned `library_metadata.libraryId` UUID. It identifies archive contents independently of their folder name. The last-opened folder preference is machine-local convenience state and is not archive payload; successful restore explicitly writes the restored path and originating installation UUID to preferences.

## Schema and integrity

Ordered, transactional SQL migrations recorded in `schema_migrations`. Never rewrite released migration history. Reject newer/non-contiguous histories rather than guessing. SQLite foreign keys enabled, WAL journal, FULL synchronous durability and a five-second busy timeout. Single app instance on an installation, single window; revision checks also protect against a second process editing a card.

Migration 1 contains installations, allocations, and cards. Migration 2 adds permanent serial reservations, one-to-one inspections, defect markers, and finalization revision/timestamp columns without rewriting migration 1. Migration 3 corrects the early inspection schema by rebuilding `inspections` with `centeringGrade` and without the obsolete `defectsGrade`/`defectsNote` columns. It preserves all meaningful inspection fields, the existing `centeringNote`, and the separate defect-marker table. It deliberately leaves `centeringGrade` null rather than copying semantically unrelated Defects data. Migrated assessment revisions advance once, so an already-finalized card becomes **changes pending** until a Centering grade is entered and the user finalizes again.

Migration 4 adds card-owned `photos` and `photo_defect_markers`. A partial unique index permits only one primary photo per card/slot while allowing unlimited null-slot Additional Photos. Primary rows cannot carry titles. Photo and marker pairs each expose `(id, cardId)` uniqueness, allowing composite foreign keys in the join table to enforce that both entities belong to the same card. Card, photo and marker deletion cascade through owned rows. The database stores relative paths, original filename, MIME type, lock state and timestamps; lock state is application workflow protection rather than a referential-integrity rule.

Migration 5 adds one immutable UUID for the library itself. Existing catalogues receive one during forward migration; the value then travels inside every database snapshot and is checked against the archive manifest during restore. Released migration SQL remains unchanged.

Migration 6 renames the eight existing inspection measurement columns to `frontVertical…`/`frontHorizontal…` and adds equivalent nullable `backVertical…`/`backHorizontal…` integer columns. It never copies Front to Back. Only previously finalized inspections have `assessmentRevision` incremented once, preserving `cards.finalizedAt` and `finalizedAssessmentRevision`; the mismatch makes the assessment changes-pending until all Back values are entered and finalization is repeated. Grades, identities, defect/photo/link rows and serial reservations are unchanged. This runs inside the existing ordered migration transaction and is idempotent through the migration ledger.

Allocations retain retired rows and allow only one current row per installation. Card rows reference their originating allocation. Card UUID/serial/allocation identity cannot be changed by UPDATE (database trigger). Serial is unique, exactly ten digits, nonzero. Numeric range/pointer values use safe JS integers; all ten-digit values fit exactly. The internal pointer may equal range end + 1 to represent exhaustion; user-configured pointers must be inside the range. Exhausted settings require a valid pointer or new range before saving.

Creation runs in BEGIN IMMEDIATE: read the current range, find the first unreserved serial at/after the pointer, insert its `serial_reservations` row, insert the card and empty inspection, advance the pointer, and commit together. The reservation records serial, originating allocation, original card UUID, assignment time, and optional deletion time. Database triggers prevent changing or deleting reservations, require a live matching reservation before inserting a card, and tombstone the reservation when its card is deleted. Allocation scans and pointer validation use reservations rather than live cards. Previously assigned serials are skipped forever, including after deletion and after manually moving the pointer backward. Ranges belonging to other installations (including historical ranges) cannot overlap in the same catalogue; this is a conservative protection. Local uniqueness does not guarantee uniqueness across disconnected catalogues; users must coordinate allocations manually.

Card metadata are nullable TEXT, including Year (free text avoids imposing unrequested identification validation). Whitespace-only values normalize to null; nonblank text preserves user formatting. Limit each field to 20,000 characters as an IPC/resource guard. No placeholders stored. Card status defaults to in_progress; includePublic defaults true. Revision and UTC ISO timestamps accompany records. The list's “Unnamed Card” is only a fallback.

## Secure boundary

BrowserWindow: contextIsolation=true, nodeIntegration=false, sandbox=true, webSecurity=true. Preload only exposes named operations, never a generic invoke API. Main validates the sender window, top-level frame and exact trusted renderer URL, plus runtime input types/ranges/field allowlists. Replies are discriminated success/error objects. SQL values are parameterized; interpolated column names come exclusively from the static metadata allowlist. Renderer navigation, new windows, webview attachment and permission requests are denied. Production CSP restricts scripts/styles to self and images to self/data plus the `cug-media` scheme. A development-only Vite transform allows its inline React preamble and hot styles; HMR websocket connections are allowed. Production builds never include the inline-script allowance. No remote content is loaded. Production ignores development URL environment overrides. No workflow shortcuts or menu accelerators for card actions. A macOS Edit menu preserves standard text-editing shortcuts; its explicit Quit menu item uses the same protected close flow.

The renderer never receives a general local-path or file-read operation. Picker results remain in main. For drag/drop, preload converts Chromium `File` objects with Electron's `webUtils.getPathForFile` and sends only those resolved paths through the private IPC invocation. Main validates type, count, extension, file size, ownership and photo slot before use.

The privileged `cug-media://` protocol accepts `GET` requests only. Its host must be exactly `thumbnail` or `original` and its path exactly one photo UUID. Main looks up that UUID in the active library database, resolves the stored relative path beneath the active library root, rejects traversal/outside-root paths, and returns the local file through Electron `net.fetch`. Ordinary grids request thumbnails; original URLs are mounted only in the selected viewer. No arbitrary local path appears in a renderer URL or API.

## Inspection and finalization

`inspections` is one-to-one with cards and cascades on card deletion. The Centering, Corners, Edges, Surface, and Estimated grades are nullable integer tenths constrained to 0–100. There is no Defects grade. Sixteen raw measurements—eight explicitly named Front fields and eight Back fields—are nullable non-negative integer hundredths of a millimeter. This keeps authoritative user values exact and makes fixed display precision deterministic. Five optional grading notes are nullable text, including one general Centering note attached to the Centering grade. Derived ratios and skew are never persisted.

Each inspection has an `assessmentRevision`. Saving a changed required grade or measurement, including the manually entered Centering grade, increments it; saving an identical value, grading notes, metadata, markers, or `includePublic` does not. Finalization validates all sixteen raw measurements, four subgrades, and Estimated Grade (twenty-one required numeric values), stores `status=finalized`, the current assessment revision, and a UTC timestamp. A finalized card is current when the stored finalized revision equals the inspection revision. A mismatch derives **changes pending** without locking edits. Re-finalizing records the new revision and timestamp.

Each defect marker has a UUID, card foreign key with `ON DELETE CASCADE`, constrained front/back side, normalized real X/Y coordinates constrained to 0–1, optional note, and timestamps. Its linked-photo count is derived for display and does not affect finalization.

The shared `faceMeasurements()` adapter extracts one face into the same eight-position calculation model. Directional ratios and apparent skew are calculated independently per face; neither face can modify the other's input or derived output. Inspection uses one stacked measurement panel with `Centering Front` above `Centering Back`. Tiny inline SVG card outlines show perpendicular double-headed border-distance arrows; the same eight `MeasurementHelper` positions are reused on each face, are decorative to assistive technology, and retain text labels and native title tooltips.

Inspection input panels follow physical border measurement order: Top, Bottom, Upper, Lower in the DOM, giving native Tab order Top Left → Top Right → Bottom Left → Bottom Right → Upper Left → Upper Right → Lower Left → Lower Right on each face. A column-flow two-row grid places Top/Upper above Bottom/Lower without focus overrides; narrow windows stack panels in DOM order. Input grouping is separate from ratio pairing: the Top and Bottom panels retain explicitly labeled Vertical Left and Vertical Right Top/Bottom ratios respectively; Upper/Lower retain their Left/Right ratios. Calculation, storage and public report ordering are unchanged.

Apparent skew assumes measurements span a typical 63.5 × 88.9 mm card. Four small-angle estimates are derived from left and right vertical border deltas and upper and lower horizontal border deltas; opposite-edge signs are normalized so positive means clockwise. Their angles are averaged. If any measurement is absent/invalid or the four estimates span more than 1°, the UI reports unavailable. Magnitudes below 0.05° display no apparent skew; otherwise the rounded one-decimal magnitude and CW/CCW direction are shown. This is a consistent visual aid, explicitly not laboratory geometry.

## Autosave and failure behavior

An editor-local controller owns a 300ms debounce, latest card/inspection/marker-note drafts, revision and a single serialized save loop. Metadata and inspection writes share the card's optimistic revision and therefore cannot race each other. Typing during an in-flight request stays in the draft and is written in a subsequent revision. Old responses cannot overwrite newer typing. Save status distinguishes pending/saving/saved/error. Failures retain the draft with a Retry action; optimistic revision mismatch blocks silent overwrite.

Card changes, library changes, configuration, marker add/remove, public-site changes, finalization, deletion and creation first flush saves. UI mutation actions are serialized. Close requests use main→preload→renderer flush handshake; main only closes when the queue drains successfully. Failure/timeout keeps the app open with a message. This protects normal close/quit, not forced process termination/power loss during the debounce interval. “All changes saved” means SQLite committed, not merely queued. No automatic backups are created.

Archive actions also run through that serialized renderer action boundary, so pending editor and note/title saves drain before the main operation starts. Main holds one archive-operation lock while a native dialog, snapshot, ZIP, validation, extraction, or library switch is in progress; ordinary mutation IPC handlers reject work during it. This provides a simple consistent database/media view without concurrent photo replacement or deletion. If normal window close or Command+Q arrives during an active archive operation, the existing save handshake runs and close waits for that operation to finish instead of terminating a staged snapshot/ZIP/restore halfway through.

Public-site generation uses the same renderer flush and main-process library-operation lock. Photo import/replacement/removal, metadata and grading mutation cannot race the eligibility query or derivative reads. Normal close/Command+Q waits for generation to finish. The renderer receives only progress/result objects over typed IPC and never receives library paths, database rows, or filesystem authority for generation.

The application menu provides normal platform editing commands. macOS Command+Q invokes the visible Quit menu action, which requests the window's protected close path. Main asks the renderer to drain autosave, keeps the app open on failure/timeout, and only then closes the window; `window-all-closed` completes application quit. The same mechanism covers other normal OS quit requests.

## Renderer workspace state

Renderer navigation uses three top-level workspaces: Library, Grading and Settings. `librarySelectedCard` owns the current read-only preview. `activeGradingCard` and its `CardAutosave` controller own the only editable card. Row selection fetches a detail DTO solely into preview state. Explicit Open card installs/replaces the editor and moves to Grading; New Card also deliberately installs its newly allocated card. Updating an active card refreshes the preview only when both IDs already match, without changing either identity.

The bounded Library page/offset stays in memory. Its database query orders by `cards.serial DESC`. Fixed-width ten-digit text preserves numeric order, and the unique serial constraint makes a secondary tie-breaker unnecessary. `updatedAt` remains persisted and indexed for display and a possible future Recently edited order, but activity never changes the default catalogue position.

A workspace scroll container records Library scroll and separate Overview, Inspection and Photos scroll values. Before top-level or tab navigation, the active autosave controller drains and the current scroll value is captured. A layout effect restores the destination value and calls `scrollIntoView(nearest)` only when needed to keep the selected Library row visible. Card Grading omits the general workspace breadcrumb so the editor begins at the top of its full-height scroll area. Serial/name plus grading/save states form the first compact sticky row; tabs form the second. This one sticky block stays inside the single scroll container, avoiding nested document/workbench scrolling. The former split-panel close control is removed because sidebar navigation owns leaving the grading workspace; the active editor remains available in session.

The active Card Editor also owns `selectedMarker`, `viewerId` and a transient targeted-marker focus request. This keeps marker selection and the viewer distinct from Library preview selection, the active card and the active tab. Inspection and Photos both resolve labels from the same card-detail Photo DTO and send a photo UUID to one shared `PhotoViewer`; Inspection therefore opens linked originals without changing its tab or selection. Photo-to-marker navigation first records the existing Photos scroll through the normal guarded tab callback, then mounts Inspection with the requested marker already selected. A request sequence allows repeated navigation to the same marker. Inspection waits one animation frame so the ordinary per-tab restoration completes, then uses `scrollIntoView` on the existing Defect Map with sticky-header scroll margin and clears the transient request. It does not create a second selection/highlight system.

The same Card Editor owns a `Set` of photo UUIDs whose linked-marker `<details>` disclosures are expanded. Photos passes each disclosure a controlled open flag, so unmounting the Photos tab does not lose browser-local disclosure state. The set supports multiple simultaneous expansions, stays independent of viewer/marker selection, resets with the keyed editor when the active grading card changes, and is pruned against the current Photo DTOs after deletion or replacement. This is session-only renderer state: it has no database, migration or IPC representation and intentionally does not survive restart.

Workspace state is intentionally session-only. Relaunch opens Card Library with no active grading card; no preferences/schema migration is added. Persisting a bare card ID in installation preferences could point at a different active library after library switching. A later restart-restoration feature would need library-scoped identity and explicit missing/deleted-card handling.

Additional Photo title changes enter the autosave controller only when the user explicitly saves Rename. Cancel never mutates the draft. Save immediately drains the same serialized title queue; blank text normalizes to null. The visible filename fallback remains derived from immutable `originalFilename`, and title updates never touch stored paths. Lock and marker-link changes are deliberate immediate operations. Tab and workspace changes flush queued drafts first. Photo rows update the card's display `updatedAt`, but photo imports, replacements, removals, locks, titles and links never increment the card's optimistic revision or the inspection assessment revision, so they cannot invalidate finalization.

Full Card tiles retain their width-driven aspect-ratio sizing. Corner and Edge preview surfaces use `clamp(180px, 22vh, 230px)` for both populated images and empty slots. Their grids remain two columns even at the application's minimum supported width; only Full Card collapses to one column at the narrow breakpoint. Thumbnail images use `object-fit: contain`, preserving the whole photograph without cropping while preventing wide windows from creating excessively tall Corner/Edge rows.

## Photo import, replacement and cleanup

Main validates and prepares every selected source before changing catalogue ownership: copy to an application-owned temporary file, generate and validate the temporary thumbnail, then atomically rename both to their final UUID paths. Only after every new file is ready does one SQLite transaction remove the superseded primary row, insert the new row(s), and update the card timestamp. A failed preparation or database transaction cleans the newly prepared files and leaves the previous photo row and files intact. After a successful replacement commit, the exact superseded row's files are removed best-effort. This prioritizes a valid catalogue reference over perfect cleanup; a rare cleanup failure can leave an inert orphan file, never a row pointing to an intentionally destroyed prior photo.

Individual removal is rejected in both service checks and the conditional delete when the photo is locked. Confirmed unlocked removal deletes the database row first, which also cascades its marker links, then removes its validated owned paths best-effort. Confirmed whole-card deletion obtains owned photo paths, commits the card cascade regardless of locks, then cleans those files and card-specific media/cache directories. Serial reservations remain separate and are still tombstoned permanently.

Photo locks prevent individual removal/replacement only. They do not change file formats, preserve revisions, restrict title/link editing, or block whole-card deletion. Replacement intentionally creates a new photo UUID and removes the old row/link records; there is no photo history in v1.

Evidence navigation reads the relationship IDs already included in the card-detail DTO. No IPC operation, persisted UI state or schema change is needed. SQLite cascades continue to remove links when either photo or marker is deleted, so renderer filtering cannot surface stale deleted evidence.

## Manual Library Archive and Restore

`.cug` archive format 1 is a standards-compliant ZIP written with streaming `yazl` and read lazily with `yauzl`; both are pure JavaScript and package unchanged on macOS, Windows, and Linux. Its paths are:

```
manifest.json
database/catalogue.sqlite
media/originals/<card UUID>/<photo UUID>.<source extension>
```

The manifest records format/application versions, UTC creation time, immutable library UUID, source folder display name, originating installation UUID/name, database migration version, compatibility fields, excluded cache declaration, and each payload's role, byte size, and lowercase SHA-256 digest. Only the database snapshot and exact original-media paths queried from that snapshot are added. Generated thumbnails, WAL/SHM files, unrelated library files, and backup archives are therefore excluded by construction. This also prevents recursive backup when the destination is inside the active library.

`Library.snapshot()` uses Node/Electron SQLite's online `backup()` API. It produces a coherent standalone database from the live WAL-backed connection instead of copying `catalogue.sqlite` bytes. The snapshot passes `integrity_check`, `foreign_key_check`, and contiguous migration-history validation before archiving. Every referenced original must exist as a regular file. ZIP output is written to a unique sibling temporary path; when replacing an existing chosen archive, that archive is moved aside and restored if final rename fails.

Restore first indexes the ZIP without extracting it. Entry names reject absolute paths, drive paths, backslashes, NUL, empty/dot/parent segments, duplicate names, symlinks/devices, encryption, undeclared payloads, excessive entry counts, and entries whose declared size differs from the manifest. Archive format and schema cannot be newer than the application. After the user chooses and confirms a separate new/empty non-symlink destination, payloads stream into a hidden same-parent staging directory. Extraction resolves every path beneath that staging root and verifies size/SHA-256 while writing.

The staged database then passes SQLite integrity, foreign-key and migration-history checks. Its schema/library/installation identities and exact photo-original set must match the manifest. Only then is the database moved to the normal library root, empty media/cache structure completed, and the staging directory renamed to the final destination. The active library is untouched until the restored `Library` opens successfully; then preferences and the in-process active library switch together. Failure removes staging and never merges with or overwrites a populated destination.

The database snapshot itself preserves workstation name, current and retired allocation ranges, next pointer, and every serial reservation/tombstone. Restore deliberately reuses its originating installation UUID so a replacement computer continues numbering. It is unsafe and unsupported to edit old and restored copies concurrently. The empty `cache/thumbnails` tree is created after restore; `photoFile(..., 'thumbnail')` regenerates a missing JPEG lazily from the preserved original when the UI requests it. No archive merge, synchronization, automatic schedule, cryptographic signature, or public filtering exists.

Format 1 begins with schema 5. A future application may accept a format-1 archive with a supported older schema and let normal migrations run when it opens the committed restored library. Unknown future archive formats or database schemas are rejected without interpretation.

## Public static-site generation

`Library.publicSiteCards()` is the privacy and eligibility gateway. Its explicit SQL projection selects public metadata and grading fields only; it does not select `submittedBy`, general card `notes`, internal UUIDs for presentation, or unlinked Additional Photos. Eligibility is `status = finalized`, `includePublic = 1`, and `finalizedAssessmentRevision = assessmentRevision`. The returned main-only source model carries card/photo/marker IDs only long enough to resolve same-card evidence relationships and library-owned originals. The renderer cannot request arbitrary source paths.

The generated structure is:

```
index.html
cards/<serial>/index.html
assets/site.css
assets/site.js
data/reports.json
data/cards/<serial>.json
media/<serial>/<slot-or-evidence-number>-preview.webp
media/<serial>/<slot-or-evidence-number>-large.webp
media/<serial>/full-front-catalogue.webp # Front photo only
.nojekyll
.cards-under-glass-site.json
```

All page, CSS, JavaScript and media references are relative (`./` from the catalogue and `../../` from report pages), so an identical directory works at a host root or below an arbitrary path. Every serial directory contains a real `index.html`; no rewrite or SPA routing is assumed. CSS, JavaScript and system-font stacks are local. The small static script filters already generated catalogue entries, normalizes all-digit queries for leading-zero-tolerant exact serial ranking, controls the native-dialog lightbox, and applies the existing marker/detail selection. Generated HTML escapes `&`, angle brackets, quotes and apostrophes. Dynamic client behavior uses DOM properties and `textContent`, never user-controlled `innerHTML`. Content Security Policy keeps scripts and other resources self-only; inline style is allowed only because generator-controlled normalized defect coordinates are emitted as responsive percentage positions.

Sharp reads authoritative originals and writes a maximum 900×900 WebP report preview at quality 82 and maximum 2400×2400 lightbox image at quality 90 for every included photo. A Front photo additionally gets one maximum 420×420 WebP catalogue thumbnail at quality 78. All derivatives auto-orient, preserve aspect ratio and use `withoutEnlargement`; non-Front photos never receive the catalogue variant. Primary slots are always represented by either a derivative or a polished placeholder. Additional Photos enter the model only through an existing defect link. A photo linked to several defects has one derivative set and multiple references. Library originals and local thumbnail cache are untouched.

The catalogue emits all reports in serial-descending order as semantic links in a responsive CSS `auto-fill` gallery. Real Front images and placeholders are absolutely contained inside an invariant 4:3 media region, so portrait or landscape intrinsic dimensions cannot alter tile geometry. Identity and Estimated Grade remain in a separate readable region. Only the 420-bound catalogue path is used as a tile `src`; native `loading="lazy"` and async decoding keep offscreen image requests bounded without coupling search to preview/lightbox assets. Search filters this static set in place and updates grammatically correct visible counts. Report identity remains an `h1` serial heading followed by a stronger `h2` Card Name.

Each `data/cards/<serial>.json` file is a strict public snapshot (current snapshot format 2/public schema 2) and the durable ownership record for one published serial. It contains the public-only report model, deterministic public fingerprint, marker ordinals, public photo roles and derivative paths, photo content identities, evidence relationships, report/image versions, and a 64-character opaque owner key. The owner key is `SHA-256("cards-under-glass-public-owner:" + lowercase immutable library UUID)`. The raw UUID never enters generated output. Because `.cug` restore preserves the immutable library UUID, a restored catalogue derives the same owner even under a different installation UUID or allocation range.

`.cards-under-glass-site.json` is site format 2/generation state 2. It owns only the reproducible global files (`index.html`, `data/reports.json`, shared assets and `.nojekyll`) and records current global format versions. Card-specific ownership is derived only from validated snapshots and their fixed serial namespaces. This avoids a single large ownership list that would allow one publisher's stale manifest to classify another publisher's files as removable.

Current snapshot inspection data requires all five grading values and sixteen face-specific measurement values. `REPORT_FORMAT_VERSION` is 3: the report renders Centering, then Corners/Edges, then the intact Defect Map section. This template-only bump refreshes report HTML using existing snapshots without reprocessing images; the image pipeline remains 1 and snapshot format/public schema remain 2. Legacy snapshot format 1/public schema 1 is an explicit separate exact-key schema with the original eight fields. Fingerprints are verified against that original payload before an in-memory rendering adapter maps those values to Front and leaves Back absent. Legacy snapshots retain their schema, owner, public data and fingerprint; template rebuilds may update their report format version and show a restrained notice that Back measurements were not recorded. No fake Back data or grading exception is created. A current schema-2 snapshot cannot omit Back fields or masquerade as schema 1. On normal Update, migrated local cards are ineligible until re-finalized and their own old reports are removed; foreign/orphaned legacy snapshots and images remain preserved and rebuildable. `.cug` format stays 1: Front/Back data and finalization history travel naturally inside the catalogue snapshot, and older restored databases run migration 6 on normal open.

Snapshot parsing requires exact keys/types, sequential marker numbers, safe deterministic media paths and a matching content fingerprint; it rejects raw/unexpected data rather than forwarding it.

`fingerprintPublicCard()` hashes a canonical JSON representation of exactly the public model: serial and allowed metadata, grades/measurements/grading notes, marker coordinates/notes, public photo roles and labels, evidence relationships, and SHA-256 identities of authoritative original bytes. Originals are streamed once per Update rather than loaded wholly into memory. Timestamps and private-only fields are excluded, so editing Submitted by or General Notes cannot invalidate output. `REPORT_FORMAT_VERSION` and `IMAGE_PIPELINE_VERSION` live beside the generator in `src/main/public-site.ts`. A report-version mismatch rewrites card HTML; an image-version mismatch rewrites public derivatives. Shared CSS/JavaScript is independent and is cheaply rewritten without forcing either version. Developers bump the relevant constant when its generated contract changes.

Normal **Update Public Site** rereads the destination snapshots on every run and derives the active owner key. It compares local eligible cards only with same-owner snapshots. A cross-owner serial match aborts during preflight before staging can commit. Local new/changed reports are written, missing local derivatives are repaired, and same-owner snapshots absent from current eligibility are removed. Every foreign snapshot, report and derivative is preserved. Report-format changes may re-render all snapshot reports because their public data is self-contained; image-pipeline changes regenerate local-owned images from originals while retaining foreign image versions and working derivatives.

**Rebuild Public Site** treats the snapshot union as its input rather than the active SQLite catalogue. It rewrites every report page plus global presentation/search assets using the current template, preserves all per-card public data, and reuses existing image derivatives. It therefore works for foreign and orphaned reports when source libraries or private originals no longer exist. A missing required foreign derivative produces a safe error instead of deleting usable content or fabricating a replacement. Both modes always rebuild `index.html`, `data/reports.json`, shared CSS/JavaScript, `.nojekyll`, and the global manifest from all valid snapshots in serial-descending order.

Before committing, managed and planned paths are validated against absolute paths, traversal, Windows drive paths, NULs, backslashes, duplicates and symlink parents. Planned generated files may replace only paths established by the global manifest or a validated per-card snapshot; an unknown conflicting file fails safely. Commit moves only managed files being replaced/removed into a sibling rollback tree, moves staged files into place, and restores the prior set if a move fails. Verified unchanged local and foreign files stay untouched. Only same-owner ineligible report/snapshot/media paths become stale during Update. Unknown files and folders, including `.git`, `CNAME` and workflows, remain outside ownership and are preserved. A failed hash, collision, derivative or build never touches the destination. Output cannot overlap the active library.

Format-1 single-library sites migrate conservatively. Legacy card paths are attributable only when their serial appears in the active library's permanent reservation ledger. Eligible matches receive snapshots and can reuse legacy fingerprints/derivatives; attributable ineligible paths are removed. Unmatched legacy report/media files are removed from generator ownership, left untouched and reported as a non-destructive warning. A subsequent externally synchronized merge should retain independent snapshots/card/media from every publisher; rerunning Update deterministically repairs stale `index.html` and `data/reports.json`. Cards Under Glass provides no distributed lock or merge engine, so users must synchronize/pull before publishing and synchronize afterward. Concurrent edits to stale directory copies remain an external-tool concern.

The typed IPC accepts only `update` or `rebuild`. The renderer drains autosaves before entering the existing exclusive library operation, so catalogue/photo mutation is paused and close/Command+Q waits. Progress distinguishes checking, changed-photo processing, report generation and catalogue writing. The completion result reports new, updated, removed and unchanged counts, or rebuilt count for a full rebuild.

This feature adds no schema migration. Its saved destination is machine-local preference state keyed by library UUID. Libraries, cards, photos and grading data remain unsynchronized; only self-contained public snapshots and derivatives coexist in the output. The application performs no external synchronization, Git, upload, hosting, authentication, public runtime database, or publisher-management operation.

## Future extension boundaries (not implemented)

- Hosting/deployment may consume the static output later, but must remain separate from eligibility and generation. No Git credentials or remote APIs belong in the current generator.

## Build and cross-platform validation

Electron-vite builds separate main, sandbox-compatible CommonJS preload and browser renderer outputs. electron-builder 26 packages `out` plus package metadata into ASAR. The canonical application version is the top-level `package.json` `version`; artifact names use `${name}-${version}-${os}-${arch}.${ext}` so every target identifies the same source version. macOS uses DMG and ZIP, Windows x64 uses NSIS, and Linux x64 uses AppImage and DEB. Linux synchronizes its installed desktop filename and Electron app ID through `desktopName`; the DEB payload uses gzip, a supported format that avoids requiring an external `xz` executable during macOS cross-packaging. Packaging output is isolated under `release/macos-<arch>`, `release/windows-x64`, and `release/linux-x64`.

`scripts/package-platform.mjs` is the release-build entry point. It safely removes only recognized generated release entries, performs one current production build, invokes every requested platform explicitly with publishing disabled, then runs structural validation. `package:all` on macOS requests all three platforms sequentially and fails the whole run if any build or validation fails; it never silently skips a platform. A failed run removes the incomplete release tree. Other hosts package their native target or use the native CI matrix because the all-target command includes macOS. `package:clean` has the same recognized-entry guard, preventing an accidental recursive delete if the output path or its contents no longer match the packaging contract.

SQLite is Electron's built-in `node:sqlite`; there is no external SQLite addon, ABI rebuild, or separately copied native binary. Sharp uses its prebuilt N-API runtime. `pnpm-workspace.yaml` requests Darwin arm64/x64, Windows x64, and Linux glibc x64 support so a macOS checkout can construct the cross-target packages. `asarUnpack` places Sharp and `@img` runtime files beside ASAR. electron-builder follows every installed optional `@img` package, so `scripts/after-pack.cjs` prunes non-target optional packages from the staged application only. The source dependency tree remains intact for the next target. Windows retains its PE x64 Sharp module/DLLs, Linux retains ELF x64 Sharp/libvips, and macOS retains its matching Mach-O Sharp/libvips pair.

`scripts/validate-packages.mjs` checks each unpacked target before a packaging command can succeed. It validates the Electron executable binary format/architecture, application name/version, the ASAR's current SQLite/archive/public-site/migration and renderer markers, the presence of exactly one target Sharp native module, the binary format of every packaged `@img` native file, required libvips files, and all configured artifact formats. It writes `release/package-manifest.json` with target details, artifact byte sizes, and SHA-256 checksums. This catches stale current-source bundles, absent/externalized image support, and foreign native binaries. It is structural package validation, not an assertion that a cross-built executable launched correctly.

The GitHub Actions matrix uses native macOS, Windows, and Linux runners. Each runner installs the same locked dependency graph, runs `pnpm check`, packages only its native target, and runs the real packaged Electron UI/relaunch suite; Linux uses Xvfb. This is the runtime verification gate for Windows/Linux. macOS can construct the current Windows installer and Linux packages using electron-builder's downloaded cross-build toolsets, but those artifacts remain only structurally/build validated until copied to the target OS or exercised by native CI.

Application paths use Node `path` APIs, Electron dialogs, `app.getPath('userData')`, and relative library/archive/site paths. Archive ZIP and public-site path validation deliberately use normalized portable entry paths and reject absolute, traversal, drive-letter, or escaping paths. No product code assumes `/Users` or a POSIX installation location. All platforms ship the same migration chain and library format; `.cug` files remain platform-independent.

Signing/notarization, installer branding/custom icon and release publishing credentials are outside this milestone; local packages are unsigned and use Electron's default icon. Do not disable Electron's sandbox to make tests pass.
